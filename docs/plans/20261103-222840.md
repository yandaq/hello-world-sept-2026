# Implementation plan: decorative pointer twinkle trail

## Outcome and normative acceptance criteria

Add a subtle, short-lived sparkle trail near the mouse pointer, coordinated with the existing aurora/sunrise palette. The implementation must:

- Preserve the native cursor, text selection, layout, message fetch, loading/ready/error treatment, and backend contracts.
- Keep decoration non-interactive, without text or focusable content, beneath the content layer and hidden from assistive technology.
- Remain dependency-free and asset-free, adding no application network requests.
- Enforce a finite live-particle limit and finite lifetime; stopping movement must leave no particles or trail-specific animation work after expiry.
- Produce no trail when reduced motion is requested. Enabling reduced motion at runtime must immediately clear particles and pending trail work; disabling it must permit subsequent mouse movement again.
- Demonstrate tracking, bounded accumulation, cleanup, reduced-motion behavior, and readable content in both color schemes with browser evidence. Existing contrast weaknesses must not be materially worsened.
- Resolve the binding contract restrictions before changing implementation files.

## Governing guidance and fixed design decisions

`AGENTS.md`, `CONTRACT.md`, `VALIDATION.md`, `docs/VALIDATION.md`, and `docs/coding-standards.md` govern this work. `docs/architecture.md` describes the current layering and stylesheet organization. Historical plans are not current requirements. The `.pi/sub-agents/` instructions apply to their respective delegated roles; conflicting generic suggestions there, including dependency installation, web fonts, or additional message states, do not override the contract.

Use dynamically created, empty `.sparkle` spans inside the existing `.backdrop[aria-hidden="true"]`. Keep `.hero` above the entire backdrop. No static markup change is expected. This keeps particles out of the accessible content and prevents direct painting over text, although their contribution through translucent glass still requires readability validation.

## Numbered implementation steps

### 1. Resolve the contract and ownership gate

**Files:** `CONTRACT.md`, `docs/coding-standards.md`; record the decision and assumptions in a new dated file under `docs/plans/`.

Have the project-scaffolder/authorized contract owner amend §§2, 6–8 before implementation. Retain frontend ownership of `public/app.js` and optional markup, and visual-design ownership of `public/styles.css`; explicitly authorize the applicable owners to maintain the affected guidance and plan documents rather than assuming unrestricted ownership.

The amendment must explicitly permit:
- Temporary empty `.sparkle` children in `.backdrop`, with stylesheet hooks and pseudo-elements for those particles.
- Decorative pointer behavior in `app.js`, separate from message state; `.card[data-state]` remains exclusively the existing message state machine.
- DOM creation/removal without HTML-string injection.
- A narrowly scoped exception allowing JS to set only particle position custom properties. All appearance, size, color, and animation rules remain in `styles.css`; arbitrary inline visual styling remains forbidden.
- Mouse-only emission, finite particle lifetime/count, reduced-motion suppression and cleanup, and unchanged API behavior.

Update the contradictory blanket prohibition on new hooks in `docs/coding-standards.md` to match this limited extension.

**Expected result:** one coherent, authorized contract permitting the feature without weakening unrelated restrictions.

**Proof:** review ownership, allowed hooks, dynamic position writes, accessibility, and state rules against the planned implementation. If the authorized owner cannot approve/apply the amendment, record that exact blocker and stop before runtime edits.

### 2. Implement bounded pointer behavior

**File:** `public/app.js` — frontend owner.

Initialize the trail independently of, and before awaiting, the existing message fetch so slow or failed requests do not prevent pointer tracking. Preserve the existing fetch and failure paths.

Listen for mouse pointer movement, emit small amounts of decoration near viewport-relative pointer coordinates, and limit emission frequency and simultaneous particles. Give every particle a finite cleanup path, including when animation events are interrupted. Clear trail nodes and pending work when reduced motion becomes active and when the page becomes hidden or exits. Do not create particles from touch input or from a stationary pointer. Do not introduce a perpetual animation loop.

**Illustrative implementation suggestion:** use one-shot CSS animation, animation-completion removal plus a finite fallback cleanup timer, and simple emission throttling. Choose modest constants in the implementation; their exact values are tuning choices, not public contracts.

**Expected result:** movement produces a bounded trail during loading, ready, and error states, with no ongoing trail work after cleanup.

**Proof:** run `node --check public/app.js`; browser assertions must verify particle creation near multiple pointer positions, the chosen live-count ceiling under sustained movement, zero remaining particles after the maximum lifetime, no further emissions while stationary, and no outstanding trail-specific timers/frames after cleanup. Exercise reduced motion both on initial navigation and through a live preference change.

### 3. Style the decorative trail without disturbing content

**File:** `public/styles.css` — visual-design owner. `public/index.html` remains unchanged unless the approved contract resolution establishes a concrete markup need.

Add compact CSS-generated sparkles with a short fade/shrink animation, using existing accent-derived tokens and scheme-specific token overrides where needed. Position particles within the fixed backdrop using the approved custom properties. Specify their order relative to sunrise/vignette while keeping the whole effect below `.hero`. Preserve pointer-event transparency and avoid layout participation, scrollbars, large blur layers, or changes to the native cursor. Add explicit reduced-motion hiding/animation suppression as a defensive CSS layer. Keep the stylesheet section index accurate.

**Expected result:** a restrained twinkle trail visible around the pointer in both schemes, without obscuring or intercepting content.

**Proof:** browser checks for coordinate alignment, viewport edges, text selection/hit testing, unchanged content geometry, and absence of overflow. Capture active-trail desktop dark/light images and mobile coverage in `/tmp`; inspect the approved hooks, stacking, and computed reduced-motion treatment.

### 4. Validate the integrated outcome and retain evidence

**Implementation files under test:** `public/app.js`, `public/styles.css`, and the unchanged page/API integration. Record results in the dated plan or implementation handoff; do not add a browser-testing dependency or committed test suite.

Run the mandatory executable checks from `docs/VALIDATION.md`, including syntax, seed idempotency, seeded HTTP/static probes, and the protected empty-database check. Use available built-in browser automation and retain console/network evidence.

Browser evidence must cover:
- Movement across separated viewport positions and over the card; sustained input respects the particle ceiling, then particles and trail work expire.
- Pointer exit/page hiding cleanup and subsequent movement recovery.
- Initial reduced motion and runtime preference toggling, including toggling while particles exist.
- Actual loading → ready behavior using a delayed message response, and readable error behavior using a controlled failed response. Confirm fetched text, status clearing/error details, and unchanged `data-state` transitions. Identify the deliberate error diagnostic separately from unexpected console errors.
- Desktop dark/light, mobile, reduced-motion, and loading/ready/error captures required by `docs/VALIDATION.md`; compare card/layout/state treatment to committed references without overwriting them.
- Paired trail-on/trail-off readability measurements in both schemes with other animations held comparable. Sample composited card padding and compare computed text colors as documented; report existing contrast limitations rather than broadening this task into a palette redesign. Verify the message remains unobscured during pointer movement.
- No new asset requests, unexpected console errors, or unhandled page errors. The documented browser favicon 404 is the existing exception.

**Expected result:** evidence maps directly to each acceptance criterion, with failed checks corrected and rerun. If browser automation is unavailable, disclose the precise blocker; static inspection and HTTP checks alone do not establish completion.

## Scope, assumptions, and risks

- Implementation scope is the client-side trail; no backend, database, dependency, asset, message API, or unrelated visual redesign is intended.
- Mouse-only behavior is the simplest interpretation of the request; touch and pen trails are not required.
- Ownership approval is a prerequisite, not something this plan silently grants. Separate frontend and visual-design delegates can implement their respective files under the amended contract.
- The existing top-level fetch await requires initialization placement to be checked carefully so loading does not delay the trail.
- Backdrop particles may be softened or partly hidden by the glass. Tune visibility without moving them above text; validate the resulting glass contrast rather than assuming layering alone proves readability.
- Existing backdrop animations continue normally. The requirement to stop after expiry applies to trail-specific animation and scheduling, not to unrelated pre-existing animation.
- There is no repository test runner or lint/type tooling. Use the documented gates and deterministic browser assertions rather than adding infrastructure.
