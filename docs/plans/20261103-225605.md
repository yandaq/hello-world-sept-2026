# Mouse twinkle trail implementation plan

## Outcome
Add a subtle, short-lived sparkle trail near the mouse pointer that harmonizes with the existing aurora/sunrise design while preserving the normal cursor, readable glass card, message loading flow, and backend.

## Governing guidance and scope
- Follow `AGENTS.md`, `VALIDATION.md`, `docs/VALIDATION.md`, and `docs/coding-standards.md`. Preserve the presentation boundaries and palette conventions described in `docs/architecture.md`.
- `.pi/sub-agents/` contains role-specific pipeline guidance, not additional runtime contracts; do not import its unrelated redesign, retry-control, font-download, or dependency-install suggestions. The dated sunrise plan is historical, not a restriction on this request.
- `CONTRACT.md` is referenced throughout the documentation but is absent from this checkout. Do not invent its contents. The current request explicitly authorizes client-side behavior and CSS changes, with HTML changes only if needed. Preserve existing DOM hooks and state semantics.

## Normative acceptance criteria
1. Mouse movement produces small sparkles close to the pointer that visibly twinkle/fade and disappear shortly afterward. A stationary pointer does not continuously emit particles.
2. Emission and live particle counts have explicit finite limits. Once particles expire, their nodes and effect-owned pending work are removed; no trail animation loop continues while idle.
3. With `prefers-reduced-motion: reduce`, no trail is emitted or animated. Changing the preference to reduce clears existing particles and cancels pending effect work; changing it back allows subsequent mouse movement to emit again.
4. The effect does not replace the cursor, intercept pointer input, enter the accessibility tree, change focus behavior, or obscure card text. It causes no layout shift or new overflow.
5. Dark and light schemes both retain a restrained, complementary effect and readable card text, without materially worsening the documented baseline contrast limitations.
6. Existing `/api/message` fetching, text-only rendering, loading/ready/error behavior, layout, and backend contracts remain unchanged. Trail initialization works even while the message fetch is pending or fails.
7. The implementation uses no dependencies, downloaded assets, additional network requests, or build tooling. Browser evidence and the documented fast checks demonstrate the outcome.

## Numbered implementation steps

### 1. Add bounded mouse-trail behavior
**Files:** `public/app.js`.

- Add a small, isolated initializer independent of the existing fetch/state code, invoked before its top-level fetch await so loading does not delay the effect.
- Handle mouse movement without changing or cancelling normal pointer behavior; ignore touch movement.
- Establish explicit limits for emission rate, live particle count, and lifetime. Each particle must expire and be removed, including when motion preferences change or the page becomes hidden.
- Observe reduced-motion preference at startup and at runtime. Clear live particles and cancel effect-owned pending work when disabling the effect.
- Keep decorative content inside an accessibility-hidden, non-interactive scope. Preserve every existing message-fetch branch and DOM hook.

**Expected result:** bounded, independently initialized decorative behavior with complete idle and disable cleanup.

**Tests:** Browser assertions exercise movement at separated coordinates, verify particles appear near recent pointer positions, stress repeated movement against the declared cap, then stop movement and verify zero remaining particles and no continuing trail-owned scheduled work. Repeat with a pending fetch and a failed fetch. Check initial reduced motion, preference changes in both directions, and cleanup when the page becomes hidden.

### 2. Style sparkles without changing content or layout
**Files:** `public/styles.css`; `public/index.html` only if an existing decorative container cannot suffice.

- Add small CSS-generated sparkle shapes with a brief finite opacity/transform animation and restrained glow. Keep all visual styling in the stylesheet; JavaScript supplies only per-particle placement/variation data.
- Derive colors from existing accent tokens, with any scheme-specific tuning expressed through tokens. Update the stylesheet section index if its organization changes.
- Define non-interactive positioning and stacking explicitly so sparkles cannot paint over readable card text or create scrollbars.
- Add explicit reduced-motion suppression rather than relying only on the existing global near-zero animation duration.
- Prefer existing decorative markup; any necessary added markup must be accessibility-hidden and non-focusable and must preserve the existing page/card tree.

**Expected result:** a recognizable but understated twinkle trail that fits both palettes without disturbing the glass card.

**Tests:** Capture active-trail desktop dark and light views and a mobile view. Move across the card and viewport edges; verify text remains unobscured, cursor styling is unchanged, hit-testing is unaffected, and dimensions/scroll overflow do not change. Inspect accessibility-hidden ancestry and lack of focusable trail content. Confirm reduced motion renders no trail.

### 3. Validate integration and record evidence
**Files/artifacts:** browser captures and validation logs under `/tmp`; a dated plan/evidence record under `docs/plans/` following repository convention. No committed browser-test infrastructure is needed.

- Run the complete executable fast check set in `docs/VALIDATION.md`, respecting its self-contained shell-line execution rules. This covers syntax, seed idempotency, API/static serving, and missing-database behavior.
- Use available built-in browser automation; do not install browser packages. Exercise the behavior checks from steps 1–2 through the served page.
- Capture the required desktop dark, desktop light, mobile, reduced-motion, and loading/ready/error views. Compare card/state treatment with the committed references without overwriting them.
- Record console/page errors and network requests. Explicitly distinguish deliberately induced message-fetch errors and the documented favicon 404 from unexpected errors. Confirm the trail adds no requests.
- Measure card contrast in both schemes using computed text colors and composited glass samples as documented. Compare equivalent trail-active and trail-disabled conditions at matched backdrop phases; this change does not require re-proving the unchanged sunrise's page-wide contribution.
- Record pass/fail evidence against each acceptance criterion, fix failures, and rerun the affected checks. Shut down servers started for validation.

**Expected result:** traceable browser evidence for pointer tracking, lifecycle, motion preferences, readability, and preserved states, plus passing runtime checks.

**Tests:** The documented fast checks and focused browser scenarios above are the completion gate. If browser automation is unavailable, report that exact blocker and the remaining static/runtime evidence; do not claim full validation.

## Illustrative implementation suggestion — not a mandate
Use dynamically created, non-focusable sparkle elements inside the existing `div.backdrop[aria-hidden="true"]`, above its vignette but below `main.hero`. A rate-limited mouse handler, finite CSS animation, and bounded expiry cleanup can avoid a perpetual animation loop entirely. Position using viewport coordinates because the backdrop is fixed. This requires no HTML changes, but the glass may soften particles beneath the card; tune their appearance outside the card rather than raising them over text.

## Assumptions, risks, and out of scope
- Assume this is a mouse-only enhancement; touch-generated effects, settings controls, and alternate cursors are not required.
- Main risks are high-frequency movement causing excess DOM work, animation cleanup interacting with the existing reduced-motion override, and sparkle light bleeding through the translucent card. Caps, explicit disable cleanup, and rendered contrast checks address these risks.
- The checkout exposes inspection tools but no browser or execution tool to this planning stage; runtime/browser checks are planned, not claimed as performed.
- Implementation scope excludes backend changes, API/state redesign, dependency changes, unrelated palette repairs, and replacing committed screenshot references. Documentation remains eligible for later revision.
