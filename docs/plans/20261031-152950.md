# Plan: bottom-left sunrise that radiates across the page

## Repo position (read first)

- `CONTRACT.md` is **binding** ("reality and this document disagree → this document wins"). It fixes the DOM hooks (§6), restricts `public/styles.css` to a known selector set plus `:root` custom properties, `@media`, `@supports`, `@keyframes` (§8), requires the stylesheet be **self-contained** ("everything is CSS-generated … no images, icons or fonts"), and assigns file ownership (§2: stylesheet = visual-design agent; HTML/JS are off-limits to it).
- Existing hooks already provide a fixed, full-viewport decorative canvas: `div.backdrop[aria-hidden="true"]` is `position: fixed; inset: 0; z-index: 0; overflow: hidden; pointer-events: none`, with `main.hero`/`.card` at `z-index: 1`.
- **Key finding — free hooks:** `.backdrop::before` is unused (only `.backdrop::after` exists, the vignette). `.hero::before` is also unused. `.grain::before/::after` are **not** usable for this: `.grain` carries `opacity: var(--grain-alpha)` (0.035–0.05), which multiplies into any pseudo-element of it.
- Warm palette already exists (`--amber: #ffb35c`, `--ember: #ff6fa5`), and the stylesheet is organised into numbered sections with a section index in its header comment — new rules belong in **§3 Backdrop** with tokens in **§1**, light overrides in **§10**, reduced motion in **§11**.

## Normative requirements (behaviour / contracts)

1. **N1 — Sunrise anchored bottom-left.** A sunrise graphic whose origin sits in the bottom-left of the page viewport, visible on first paint without scrolling, at every viewport width from 320px to widescreen.
2. **N2 — Radiates across the whole page.** Its light (rays and/or halo/wash) must spread across the full viewport toward the top-right — a page-wide radiation, not a confined corner blob.
3. **N3 — Purely decorative.** No text, no new DOM nodes/ids/classes/attributes, no interaction, no additional HTTP request. Achieved inside the existing `.backdrop` scope so it stays behind `main.hero` content.
4. **N4 — Contract-conformant.** No change to `public/index.html`, `public/app.js`, `src/**`, `package.json`, or `CONTRACT.md`. No `@import`, no web fonts, no new asset files, no dependencies, no build step. (Consequence of `CONTRACT.md` §2/§6/§8, not a general file freeze: if a doc statement elsewhere becomes inaccurate, fix it rather than leave it wrong.)
5. **N5 — Both colour schemes.** Deliberate, legible sunrise rendering under `prefers-color-scheme: dark` **and** `light`.
6. **N6 — Reduced motion.** Under `prefers-reduced-motion: reduce` the sunrise still renders (static, intentional-looking), consistent with the existing §11 pattern.
7. **N7 — No regressions.** Existing behaviour untouched: the three orbs + grain + vignette still read, `loading` / `ready` / `error` card states look as they do today, `#message` renders, `/api/message` and static routing unchanged, card text contrast not degraded by the new glow.

## Illustrative approach (suggested, not mandated)

A CSS-only sunrise built from stacked gradients on the unused `.backdrop::before`, sharing one origin point so the sun disc, halo, horizon wash and radiating rays all emanate from the same corner. A second layer on `.hero::before` is available if independent motion of the rays is wanted. Nothing below is prescriptive beyond the hooks and constraints above.

### Steps

**Step 1 — Sunrise tokens** → *file:* `public/styles.css` (§1 `:root`, plus §10 light block)
Add a small token set so both palettes can be tuned independently, e.g. `--sun-x`/`--sun-y` (corner anchor, e.g. `8% 100%`), `--sun-reach` (viewport-relative radius, `vmax`-based), `--sun-core`, `--sun-glow`, `--sun-ray`, `--sun-alpha`, `--sun-blend` (mirror the existing `--orb-alpha` / `--orb-blend` pattern; `screen` dark, `multiply` light). Derive colours from existing `--amber` / `--ember` so the sunrise harmonises rather than introducing a fifth hue.
*Outcome:* one place controls the sunrise; §10 override exists.

**Step 2 — The sunrise layer** → *file:* `public/styles.css`, new block in §3 Backdrop
Style `.backdrop::before`: `position: absolute; inset: 0` (or slightly negative-inset to avoid `overflow: hidden` clipping), `pointer-events: none`, `mix-blend-mode: var(--sun-blend)`, `opacity: var(--sun-alpha)`, with stacked `background-image` layers — radiating rays (`repeating-conic-gradient(from … at var(--sun-x) var(--sun-y))` with transparent gaps), sun core (`radial-gradient(circle at …)`), halo, and a low horizon wash along the bottom edge, each sized via `--sun-reach` in `vmin`/`vmax` so the radiation scales with the viewport and reaches the top-right corner (N1, N2). Prefer gradient alpha falloff over an added full-viewport `filter: blur()` (the orbs already blur heavily; a third viewport-sized blurred fixed layer is needless paint cost).
*Outcome:* sunrise visible bottom-left and washing the whole page, behind all content.

**Step 3 — Layer order vs. the vignette** → *file:* `public/styles.css`
`.backdrop::after` (vignette) paints after `.backdrop::before`, i.e. **on top of** the sunrise, and its darkest region is exactly the corners where the sun lives. Resolve explicitly — either give the sunrise and vignette pseudo-elements explicit `z-index` values inside `.backdrop`'s stacking context (`.backdrop` is `position: fixed; z-index: 0`, so it forms one), or soften/shift the vignette so it stops crushing the warm glow. Confirm the sunrise never paints above `.card` content.
*Outcome:* sunrise survives the vignette (N2) while staying behind `main.hero` (N3) and leaving card legibility intact (N7).

**Step 4 — Optional gentle motion** → *file:* `public/styles.css` (§8 Keyframes + §11)
If wanted: a slow opacity/`brightness` breathing on the sunrise layer, or a very slow `rotate` with `transform-origin` at the sun anchor — on `.backdrop::before`, or on a separate `.hero::before` layer (fixed, `z-index: -1` within `.hero`) if the rays must rotate independently of the static glow. Keep it subtle and slow. **Do not** register a new `@property` to animate a gradient angle: `@property` is outside the constructs `CONTRACT.md` §8 lists. Omitting animation entirely is acceptable.
*Outcome:* life without motion overload and without contract drift.

**Step 5 — States, responsiveness, reduced motion, light mode** → *file:* `public/styles.css` (§9, §10, §11)
- Leave the sunrise uncoupled from `.card` `data-state`; the existing `error` treatment already recolours `.orb--1`/`.orb--2` via `:has()` and needs no sunrise counterpart (smallest change, N7). If the warm error palette visibly clashes in testing, dampen `--sun-alpha` under `.page:has(.card[data-state="error"])` only.
- Use `clamp()`/viewport units so the anchor stays in the corner at 320px–1800px+; extend the existing `max-width: 640px` block if small screens need lower alpha or shorter reach.
- Light mode: warm low-alpha wash rather than a blown-out white sun; verify glass-card text contrast still holds (target WCAG AA, per the repo's visual-design guidance).
- Reduced motion: the global §11 rule collapses durations so an animated layer lands on its end keyframe — set an explicit static sunrise appearance there, mirroring the existing `.card::after` / `.message` overrides (N6).
- Keep the file's header section index accurate if a new section heading is introduced.
*Outcome:* the feature is deliberate across schemes, sizes and motion preferences.

**Step 6 — Documentation** → *files:* `README.md` (only if its description of the page becomes inaccurate), `docs/architecture.md` (no module change expected)
No functional doc change is implied: `README.md`'s layout table and `CONTRACT.md` §6/§8 remain literally true for a CSS-only change. Record the approach in the commit/report rather than amending the contract.
*Outcome:* docs stay truthful; contract untouched.

### Assumptions & risks

- **"Sunrise graphic" = CSS-generated graphic**, per `CONTRACT.md` §8's explicit self-contained / no-image requirement and the repo's all-CSS backdrop. A literal SVG/`<img>` sunrise would require amending `CONTRACT.md` §6 (new DOM) and §8 (local asset) and editing `public/index.html` — out of scope; raise it as an explicit contract change if the requester insists on a drawn illustration.
- **Main visual risk:** the existing vignette darkening the sunrise (Step 3). Judge from screenshots, not code.
- **Secondary risks:** light-mode overexposure; large blended/bloomed layers costing paint on mobile (keep alpha low, avoid extra full-viewport `filter: blur`); `mix-blend-mode` interacting with the card's `backdrop-filter` so the glow bleeds into the glass — acceptable if contrast holds.
- `.grain::before/::after` are unusable for this (parent `opacity: 0.05`); noted so the implementer does not lose time there.
- No browser test suite or linter exists in the repo; do not add one for a CSS-only change.

## Addendum — loop 2 (validation gate, after rebase onto main)

The stylesheet work landed in loop 1 and survived review unchanged. What failed was the validation
gate itself, not the page: `sf`'s gate (`sf.target.validation_commands`) takes every non-comment
line of every `sh`/`bash`/`shell` fence in `docs/VALIDATION.md` and runs **each line in its own
`/bin/sh -c` process**, so the multi-line bash fence this plan's validation section implied could
not work — `PORT=…` / `LOG=$(mktemp)` did not reach the line that used them (an empty `>"$LOG"`
redirect produced `: No such file or directory`), and `for … do` never reached its `done`
(`syntax error: unexpected end of file`). Both fences were rewritten so that every line is a
self-contained POSIX `sh` command that starts what it needs, probes, cleans up through its own
`EXIT` trap and ends with `[ "$fail" -eq 0 ]`; the empty-database 503 probe is now part of the
executable set instead of prose-only advice, and it restores `data/hello.db` even when it fails.
The fence also gained a pre-flight that refuses to run while something else is serving `:3199`: a
foreign server answers the route probes but has no listen log, so the gate otherwise failed with the
confusing `FAIL listen log line count: expected [1], got [0]` — which is exactly how a dev server
left on 3199 during this loop made the gate fail before it was diagnosed. Testing the fences both
line-by-line and pasted into one `set -eu` script also showed a cleanup `trap` must guard each of its
commands (`… || :`): a failing `kill` inside the trap aborted the remaining restore under `set -e`
and stranded `data/hello.db` in its `mktemp -d` directory. No product file changed for any of this.

Measured evidence, recorded because it corrects two assumptions in the original validation section:

- **Contribution is measurable page-wide, not just in the corner.** Toggling the layer off on the
  same page (`animations: 'disabled'`), all 960 cells of a 48×20 grid over the dark 1440×900 render
  gain light: mean +0.013 luminance, peak +0.123 (+913% relative) at the anchor, while the far
  top-right corner still lifts ~+0.001–0.002 absolute (≈ +6–20% relative). The bottom-left corner
  sample moves from luminance 0.0031 to 0.0274 and its warmth (R−B) from −5 to +21. In light mode
  every cell is warmed and darkened by the `multiply` wash (mean −0.045). Reduced motion pins
  `opacity: var(--sun-alpha)` with no transform, as §11 intends.
- **Two pre-existing findings, neither introduced here.** (1) Chromium fetches `/favicon.ico`
  because the contract-fixed markup carries no icon link, so the console shows one 404 error and
  the page's own request list stays at `/`, `/styles.css`, `/app.js`, `/api/message`. (2) Muted ink
  over the glass measures 2.9:1–4.6:1 (dark) and 4.2:1–4.5:1 (light) depending on which orb sits
  behind the card; the sunrise moves those numbers by ≤0.6 ratio points and leaves the worst-case
  patch's margin where it was (0.67× → 0.65× of AA in dark, 0.92× → 0.90× in light). Both are now
  documented in `docs/VALIDATION.md` as expected/known rather than re-diagnosed per run.
